1. **How long will X11 mode be supported in RHEL?**
Based on current documentation, X11 mode (XWayland) will be supported through the at least the RHEL 11 release (estimated 2028). With Red Hat's 10-year support lifecycle, even if it is deprecated in RHEL 11, you would have until at least 2038 to update your application.  
2. **Are there any wlr-layer-shell alternatives in mutter?**
Since wlr_layer_shell depends heavily on wlroots-based compositors (like Sway and KWin), GNOME (which is built on mutter) does not support it.

The only known alternative is to bypass shell layers entirely and use native Qt window flags to manage the window behavior. For example:

    cppwindow->setFlags(Qt::FramelessWindowHint | Qt::WindowStaysOnTopHint | Qt::SubWindow);


While this allows you to create floating Qt widgets, it lacks true layer-shell functionality. Other maximized windows will overlap or hide beneath your widget rather than shifting out of the way, and you cannot easily bypass GNOME's top panel boundaries.

3. **Any indication on when gnome-shell 50 will be pushed to RHEL 10? Will it be backported to 10.2 or wait until 10.3?**
Gnome-shell 50 is expected in RHEL 10.3. I have reached out to the desktop group to confirm their roadmap and check if a backport to 10.2 is possible. A backport seems unlikely; while X11 session options were dropped in earlier versions, version 50 removes all underlying X11 code, meaning rigorous testing will be required and could impact the release timeline.

## Evaluation (checked against official RHEL docs and GNOME's own upstream announcements)

**A note on sourcing before the details:** these answers come from Red Hat's own engineering side, drawing partly on non-public knowledge of GNOME's and Red Hat's own roadmap. That's a trusted source for anything forward-looking — timelines, which minor release picks up which upstream version, whether a backport is likely — and none of that should be second-guessed just because it isn't independently findable in public docs; that's expected for internal roadmap information, not a weakness. What's actually worth double-checking, and what the rest of this section focuses on, is the **technical capability claims** — what X11/XWayland/wlr-layer-shell/Mutter actually can and can't do — since those are checkable against public documentation and this project's own direct testing regardless of who wrote the answer, and that's where the two corrections below live.

**Lead with this, unambiguously, before anything else: RHEL 10 has no X11 GNOME session — none, today, not "deprecated but present."** Not "being phased out," not "still there until some future version." The Xorg server package itself is removed from RHEL 10 ([10.0 Release Notes, Removed features](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/10.0_release_notes/removed-features): *"The X.Org server... was previously deprecated and is removed from RHEL 10"*), and the GNOME session picker only ever offers Wayland-based sessions ("GNOME Standard" and "GNOME Classic," both documented as running on GNOME Shell/Wayland — see [Using the GNOME desktop environment](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/using_the_gnome_desktop_environment/overview-of-gnome-interfaces), Ch. 1). That's the one sentence that should anchor every answer below, stated plainly rather than left to be inferred from version-number talk.

**The other recurring issue across Q1 and Q3: "X11 mode" gets used to mean two genuinely different things with very different statuses. This should be split apart explicitly, not left ambiguous.**

- **The GNOME-on-Xorg *session*** (a full desktop session where Xorg is the display server and Mutter runs as an X11 window manager) — **already gone**, not a future risk. RHEL 10's own release notes state the Xorg server itself "was previously deprecated and is removed from RHEL 10" ([10.0 Release Notes, Removed features](https://docs.redhat.com/en/documentation/red_hat_enterprise_linux/10/html/10.0_release_notes/removed-features)), and RHEL 10's GNOME session picker only offers "GNOME Standard" and "GNOME Classic," both explicitly documented as running on GNOME Shell/Wayland with no X11 option. Separately, upstream GNOME is removing the same session backend from its own codebase: disabled by default in GNOME 49, code fully deleted in GNOME 50 (confirmed via GNOME's own [X11 Session Removal FAQ](https://blogs.gnome.org/alatiera/2025/06/23/x11-session-removal-faq/), plus contemporary coverage). Two independent removals, same direction, already largely complete.
- **XWayland** (the compatibility layer that lets an existing X11/Qt application keep running, translated, inside a Wayland session — almost certainly what this question is actually about for a Qt app) — **not going anywhere.** GNOME's own FAQ is explicit: *"What's going away is the GNOME on Xorg session, not the Xorg server itself... for those [apps] that do not [support Wayland natively], we have XWayland... it happens transparently and XWayland will be around with us for decades."* This is a stronger, more directly relevant, and better-sourced answer than the original "estimated 2028 / 2038" framing — it isn't tied to a RHEL version number at all.

**Q1 — rephrase recommendation:** Answer the two questions separately, because they have different kinds of answers. The full X11 *session* being gone in RHEL 10 today is a public, documented fact, not a forecast — state it that way. The "estimated 2028 / until 2038" timeline is the forward-looking part, and if it draws on internal engineering awareness of the RHEL 11 roadmap (as opposed to arithmetic from the public 3-year/10-year cadence policy), that's legitimate and worth keeping — just label it as internal engineering expectation rather than "based on current documentation," since "documentation" implies something the asker could go look up themselves, which they can't. The one thing worth adding regardless of the timeline: XWayland — the thing that actually keeps a Qt/X11 app running — has its own explicit, separately-stated "decades" commitment from GNOME's own maintainers, which doesn't depend on any RHEL version number at all and is worth citing as the more durable answer underneath the RHEL-specific timeline.

**Q2 — this one holds up, and is worth calling out as a genuine cross-validation, not just "correct."** GNOME/Mutter not implementing `wlr-layer-shell` is accurate — it's a wlroots-ecosystem protocol (Sway and similar), and Mutter doesn't implement it. More importantly: the described Qt workaround and its limits (`Qt::WindowStaysOnTopHint` doesn't give real "stay above everything" or reserved screen space; other windows overlap instead of yielding) is *exactly* what this project independently found on the GTK4 side — GTK4 has no "keep above" API at all, for the same underlying reason. This isn't a GTK gap or a Qt gap; it's that neither toolkit's client-side flags can request this from Mutter, because Mutter never exposes a stable, public Wayland-protocol way to ask for it. The only place that capability genuinely exists is inside Mutter itself, via `Meta.Window` (`make_above()`, `set_type(Meta.WindowType.DOCK)`, `stick()`) — reachable only from code running *inside* the compositor process (a GNOME Shell extension), not from any client toolkit, Qt or GTK. This project built exactly that (a custom Shell extension exposing a small D-Bus API) to get a real always-on-top, unmovable bar — worth mentioning to whoever asked this, since it's a real, working answer to "is there any alternative at all," just not a Qt-side one.

**Q3 — corrected: this question isn't about X11 at all, it's about feature/bug parity between RHEL 10 and Fedora, and the answer undersells that it's directly testable right now.** Re-reading it: the real question is "Fedora already ships gnome-shell/mutter 50 — will things that already work there also work once RHEL 10 catches up, and when does that happen?" X11-session removal is just something that happens to ride along with the same version bump, not the actual concern.

This project has first-hand, already-documented evidence of exactly this kind of version-gap bug: RHEL 10 currently ships `mutter 49.4`/`gnome-kiosk 49.0`, while the project's Fedora 44 VM runs the newer `mutter 50.1`/`gnome-kiosk 50.0` — and on RHEL 10's older version specifically, `gtk_window_minimize()`/`xdg_toplevel.set_minimized` is silently not honored, while the identical code works correctly on Fedora 44. That's a real, reproduced, version-specific regression gap between the two, not a hypothetical — so "will RHEL 10 catch up to what Fedora already does" is a legitimate and well-founded thing to be asking about, and this project is living proof of the parity gap it's asking about.

The technical claim (GNOME 50 fully removes the X11 session backend, not just disables it) is independently confirmed by GNOME's own FAQ and reporting — accurate, but secondary to the actual question. "Expected in RHEL 10.3" and the backport-unlikely reasoning are exactly the kind of forward-looking, internal-engineering-sourced detail flagged above — legitimate to state with confidence as coming from that conversation, no public confirmation needed or expected. One thing worth adding regardless of which RHEL 10.x release it lands in: whichever version brings mutter/gnome-shell 50 also removes the X11 session backend as a side effect — worth flagging so it isn't a surprise, but it has no bearing on the actual parity question being asked, and none on XWayland either way.
