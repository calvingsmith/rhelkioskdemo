Technical briefing — window management on RHEL 10

From Motif to Mutter

What changes when a Motif/X11 desktop application has to run on a modern GNOME/Wayland compositor — and what it takes to close the gap.

Window management GTK4 / Wayland RHEL 10
02

The need

Kiosk software still expects a 1990s window manager

Long-lived kiosk and control-room applications were built against Motif/X11 conventions — an application-managed desktop where the client program places windows at exact coordinates, pins panels above everything else, and owns much of what would today be called "the desktop."

RHEL 10 retires the platform that made those conventions possible. Any application carrying that assumption forward needs a clear account of what changes, what simply no longer exists, and what has to be rebuilt on top of the compositor GNOME now owns exclusively.

03

Framing

Two window-management models, not two skins

The change is architectural before it is visual: who is allowed to decide where a window sits, and how it behaves.

Motif / X11

The application is the window manager's peer.

Clients request placement and state directly through the X protocol. A separate, swappable window manager (mwm) enforces policy, but many applications talk past it with their own hints and direct calls.

GNOME / Mutter (Wayland)

The compositor is the only authority.

Mutter is simultaneously the display server, the window manager, and the compositor. A client can request things, but the compositor decides — and most placement and stacking requests have no protocol representation at all.

04

Platform fact

There is no GNOME-on-X11 session in RHEL 10

  • The Xorg server package is removed from RHEL 10 (RHEL 10.0 Release Notes, "Removed features").
  • RHEL 10's GNOME session picker offers only Wayland-based sessions — "GNOME Standard" and "GNOME Classic" — with no X11 option.
  • Upstream GNOME is removing the X11 session backend from its own codebase on the same schedule: disabled by default in GNOME 49, deleted entirely in GNOME 50 (GNOME, "X11 Session Removal FAQ").
  • Motif and mwm are separately documented by Red Hat as deprecated ("Motif packages are deprecated"); the motif-static package has been removed, and Red Hat's own guidance names GTK as the replacement toolkit.
05

Platform fact

XWayland is a compatibility layer, not a fallback session

  • XWayland lets an existing X11 binary keep running, translated, inside a Wayland session. GNOME's own project FAQ states it plainly: "what's going away is the GNOME on Xorg session, not the Xorg server itself … XWayland will be around with us for decades."
  • It is not a standalone X server — there is no independent Xorg process to point a separate window manager at, and no supported way to run mwm as the session's actual window manager (Red Hat's own MWM-on-RHEL how-to covers RHEL 7–9 only, with no RHEL 10 continuation).
  • An unmodified legacy X11/Motif binary can still launch and draw under XWayland. What it cannot do is gain any new window-manager-level capability from the host session — those requests still terminate at Mutter, not at a real X11 window manager.

07

Migration checklist

What a developer has to change

  • Re-platform the toolkit.Xt/Motif widget code has no supported path forward on RHEL 10; Red Hat's documented direction is GTK4.
  • Remove dependence on absolute placement.Any logic that sets or reads window x/y in screen coordinates has no client-side equivalent, and needs to be redesigned around compositor-driven placement or an in-application layout model.
  • Remove "always on top" as a client-side request.No Wayland client protocol grants this; a stays-above-all requirement has to move out of the application process entirely.
  • Treat window-state requests as advisory, not guaranteed.Minimize, stacking, and similar hint-based requests can be silently ignored by the compositor, and the same request can behave differently across compositor versions.
  • Drop direct Xlib/Xt/X-protocol calls.Replace with GDK/GTK4 equivalents; libraries that assume a live, standalone X server process are not supported going forward.
  • Re-architect multi-pointer or multi-seat input designs.Wayland's one-seat-per-session model has no Multi-Pointer X equivalent; per-device input identity is not available to an ordinary client.
  • Scope XWayland correctly.Useful as a bridge to keep an unmodified legacy binary running — not a foundation for new window-management functionality.
  • Plan for compositor version differences.A hint honored on one shipped Mutter version is not guaranteed on another, including across RHEL 10 point releases.
08

The gap

Some capabilities only exist inside the compositor process

A defined set of window-management capabilities exist as real, documented operations on Mutter's internal window object — but only for code running inside the compositor itself. No Wayland client protocol exposes an equivalent request to ordinary applications, regardless of toolkit.

The only supported way to reach that internal API from application logic is a GNOME Shell extension: JavaScript running in-process with the compositor. RHEL 10 documents installing and enabling such extensions system-wide as a standard administrative task ("Enabling and enforcing GNOME Shell extensions").

In-process only: absolute get/set window position · forced above-all stacking (dock-style pinning) · enforced minimize/restore
09

Consequence

One application becomes two coordinated programs

  • Application logic now spans two runtime domains: the ordinary GTK4 client process, and JavaScript running inside the compositor as a Shell extension — different language, different process, different lifecycle.
  • Any capability that needs the in-compositor API has to cross that boundary through an explicit interface, typically D-Bus, instead of a single in-process function call — a message contract to define, version, and keep in sync on both sides.
  • The extension and the application ship, version, and get enabled or disabled independently of one another — more moving parts to deploy and keep compatible than a single-process client application has.
  • The extension's correctness depends on Mutter/GNOME Shell internals rather than a stable public protocol — an internal API, not bound by the same compatibility guarantees as a documented Wayland protocol.

A Shell extension closes most of the gap left by the client protocol — but not all of it. Fusing the window manager into the compositor, and Wayland's one-seat-per-session model, are architectural choices an extension operates inside of, not around.

11

Discussion

A supported shim would change the shape of this problem

The capabilities most legacy Motif/X11 kiosk and control-room applications actually need are a small, well-defined set: absolute window position, stays-above-all pinning, and reliable minimize/restore. Reaching any of them today requires each project to independently author, ship, and maintain its own GNOME Shell extension against Mutter's internal API — an internal surface with no compatibility guarantee, re-derived from source by every team that needs it.

A Red Hat-supported alternative would look like one officially maintained GNOME Shell extension, exposing a small, stable, versioned interface for exactly this capability set, packaged and updated in step with each RHEL point release. Paired with a thin client-side library, an application would call a documented, supported API instead of re-implementing compositor-internal logic and an ad hoc IPC contract per project. Compatibility across Mutter versions — the same version skew visible between what RHEL 10 ships and what upstream GNOME already supports — would become Red Hat's maintenance surface instead of every downstream team's.

This does not restore Motif or X11. It narrows the gap between what legacy window-management code expects and what a supported RHEL 10 desktop can actually grant, down to one documented interface instead of one bespoke extension per application.
